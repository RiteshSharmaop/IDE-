## Docker Executor: socket hang up — cause and fix

Summary
- Symptom: Postman reports "socket hang up" or empty response when calling the execute endpoint.
- Root cause: server process restarted while handling the request, closing the HTTP socket.

What happened
- The original implementation copied submitted code into the container's `/execution` folder by running `docker cp` (or writing files into the host `./execution` folder).
- In this project `./execution` is mounted into the `code-executor` container and is also watched by the backend's `nodemon` process.
- When the backend writes a file into the host-mounted `./execution` folder, `nodemon` detects a file change and restarts the backend process. That restart closes open HTTP connections and results in the client seeing `socket hang up` or no response.

Other contributing issues
- Using `exec`/`execPromise` to run long-running commands can hit stdout/stderr buffer limits and obscure streaming I/O. That can make input piping and timeouts fragile.
- Spawned processes without `error` listeners can raise uncaught errors that crash or hang the Node process.

What was changed to fix it
1. Avoid writing into the host-mounted `/execution` directory. Instead stream the submitted code into the container's `/tmp` via `docker exec -i sh -c 'cat > /tmp/<file>'`. This does not touch the watched host folder so `nodemon` will not restart.
2. Use `spawn` for `docker exec` so stdin can be piped reliably and data can be streamed (stdout/stderr handlers receive chunks). Add `error` handlers on spawned processes to avoid uncaught exceptions.
3. Add a controlled timeout that kills the process (SIGKILL) if execution exceeds the configured limit, and perform deterministic cleanup of the temporary container file.
4. Add debug logging for `docker cp`/`docker exec` args, stdout/stderr chunks, and timeout events to help diagnose future issues.

Why this fixes the socket hang up
- Because we no longer modify the host-mounted folder watched by `nodemon`, the backend process will not be restarted in the middle of handling a request. That prevents sudden socket closure.
- Using `spawn` with proper handlers and timeouts prevents buffer-related hangs and uncaught exceptions.

How to verify
1. Restart backend and reproduce the request in Postman. You should see `[dockerExecutor]` logs for streaming, stdout chunks, and the final exit code instead of a nodemon restart.
2. Watch for absence of `nodemon restarting due to changes...` messages during a single request.

Files changed
- `backend/src/services/codeExecutor/dockerExecutor.js` — switched to streaming into container `/tmp`, spawn-based `docker exec`, added logging and robust cleanup.

If the problem persists
- Paste the backend console output (lines with `[dockerExecutor]` and any `nodemon` lines) and the controller snippet that calls the executor.
